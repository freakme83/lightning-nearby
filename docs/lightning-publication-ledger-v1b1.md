# Publication Ledger / Duplicate Protection v1B.1

This research-only domain layer represents a completed dry-run observation as a `PublicationRecord` and compares it with records supplied by a caller. It answers whether two records identify the same observation strongly enough to avoid a repeat publication. It does not publish, load, or save anything.

## Record and identity

The builder requires the completed end-to-end result, its exact composer text and its v1A shadow decision. It records the incident reference time and coordinate, enrichment status, existing selected Xweather event ID/type when present, location label, run ID when supplied, and recording time. The current builder emits only `WOULD_PUBLISH` or `HOLD`; `PUBLISHED` and a platform post ID are reserved for a future real publisher. A shadow `WOULD_PUBLISH` is **not** evidence that a post exists.

`publicationId` is `pub_` plus the first 32 hex characters of SHA-256 over a versioned JSON tuple of run ID, run-local incident ID, observation time/coordinate, selected event ID and message fingerprint. It is deterministic for the same input, independent of `recordedAt`, and is never simply the incident ID. A supplied run ID distinguishes records from different workflow runs. Without one, identical inputs may produce the same record ID; a future storage caller should supply the run ID. The fingerprint is SHA-256 of the **exact UTF-8 composer text**, including whitespace and line breaks. It is an identity aid, not a security feature or a sufficient duplicate rule by itself.

Run-local IDs such as `i-000001` can recur in different runs. The duplicate matcher does not compare them. It first matches the same non-null selected provider event ID within the same provider (currently Xweather), regardless of run or local incident ID. If a selected ID is missing on at least one side, it can match only when the exact message fingerprint agrees **and** reference times differ by at most 2 seconds **and** incident coordinates are at most 250 metres apart. Two different non-null provider IDs do not fall back to the weaker fingerprint rule. Provider IDs are taken from the existing selected `enrichment.match`; `no_match` has none. No extra selection or provider call occurs.

For example, run 1 has `i-000002`, selected event `abc123` and shadow `WOULD_PUBLISH`. Run 2 has `i-000001` and the same selected event `abc123`. When a future caller supplies the first record as prior publication history, the match is `same_provider_event` and its `knownDuplicate: true` context makes v1A return `HOLD`. Merely storing a shadow record would not mean a real post was made; a future persistence layer must decide which records represent actual publication history.

By contrast, a new observation 3 km away several minutes later is not automatically a duplicate, even in the same storm, district, or locality. Reactivation alone is not duplication either. Ambiguous identity passes through: a false-negative duplicate is preferable to suppressing genuinely new nearby activity. There is no nearby cooldown or storm-cell suppression in this module.

`matchPublicationDuplicate(candidate, priorRecords)` is pure. Its result contains `duplicate`, `reason` (`same_provider_event`, `same_observation_fingerprint`, or `no_duplicate`), and `matchedPublicationId`. `duplicateDecisionContext(match)` passes that boolean to the pure v1A gate. The current GitHub Actions workflow still has no persistent history and performs no cross-run duplicate check. v1B.2 will choose a real store; v1B.1 adds no database, credentials, ledger file, social API, or publishing integration.
