# Publication Ledger v1B.2: persistent shadow history

The manual Research Lightning End-to-End Dry Run now uses the existing private Supabase `public.publication_records` table. Its server-side step receives `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` from GitHub Actions secrets; neither secret is sent to the Job Summary or artifacts. RLS remains enabled, with no public/anon policies added. Nothing is posted to social media.

After the existing composer creates its exact message, the runner builds a provisional record, reads narrowly scoped history, calls the unchanged v1B.1 duplicate matcher, recomputes the final v1A shadow decision, and inserts the final record. The original pipeline status and composer text are unchanged. `ledger` diagnostics in the result and Job Summary show history, duplicate match, storage status, and persisted publication ID separately from the final shadow decision.

For a selected provider event ID, history is filtered by provider, event ID, and blocking decisions. A second lookup filters by exact message fingerprint and incident reference time within ±2 seconds; the pure matcher checks the final 250-metre distance and refuses to conflate distinct non-null provider event IDs. Queries are capped at 100 rows each; an overflow fails closed. `HOLD` rows are retained for audit but cannot block. `WOULD_PUBLISH` shadow rows and future `PUBLISHED` rows can block. An unrelated incident nearby, or reactivation without a matching record, remains eligible. There is no nearby cooldown.

The adapter explicitly maps camelCase record fields to the table's snake_case columns. The existing primary key on `publication_id` supports idempotent insert-if-absent writes; immutable existing records are not overwritten. The one schema addition is `scripts/lightning-publication-ledger/migrations/20261008_provider_event_unique.sql`, applied to the prepared Supabase project. Its partial unique index reserves `(provider, provider_event_id)` only for `WOULD_PUBLISH` and `PUBLISHED`. It allows any number of `HOLD` audit rows for the same event. If concurrent runs both initially see no provider-ID match, only one blocking insert can win. On a failed insert the runner re-reads history and reports a final `HOLD` with `publication_record_unavailable`, plus `duplicate_incident` if the other run's record appears; it tries to persist a `HOLD` audit row. A retry of the exact same publication ID is successful and leaves the original immutable row intact.

Missing configuration or a failed history read yields `HOLD` with `publication_history_unavailable`; a failed write yields `HOLD` with `publication_record_unavailable`. Neither is silently treated as no duplicate. Storage is skipped entirely for a pipeline outcome without a completed message. The partial index protects same-provider-ID races, but strict fingerprint fallback has no atomic uniqueness constraint, so two concurrent no-ID observations can both initially decide `WOULD_PUBLISH`. No publisher exists in this milestone; a future publisher must address that remaining race before publishing.
