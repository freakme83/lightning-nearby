# Ankara Activity Watch v1

Activity Watch is an opt-in observer of the already decoded Blitzortung stream on the existing Ankara worker. `ACTIVITY_WATCH_ENABLED` defaults to disabled; this PR does not enable it. The existing Continuous Capture archive, candidate/incident lifecycle and publications have no dependency on its database responses. There is no second socket, backfill, notification, export or publisher.

## State and time

`idle` means no active row, `active` is the one open row, and `closed` is a finalized historical row. Only a technically valid event inside the existing Ankara monitoring polygon whose receive-minus-event latency is between 0 and the production Blitz admission freshness limit (30 seconds, inclusive) is offered to the watch. It does not reuse the production admission's in-memory dedupe or call its lifecycle callback. The same source fingerprint, SHA-256 hashed, is unique in the watch's event table and matches `continuous_capture_strikes.event_key`. These are observed detections, not inferred unique physical discharges. Independent asynchronous archive writes mean no foreign key to the archive; a watch event may be present when its archive write was lost or not yet committed.

The first eligible event opens a period at its event time. Distinct eligible events increment its count once and advance `last_detection_at` to the greatest actual event time. The database serializes sync operations under one advisory transaction lock and enforces one active period with a partial unique index. The inactivity threshold remains **30 minutes since the last eligible event**. The RPC first accounts for any queued eligible events, then checks closure; an event beyond an already established 30-minute boundary starts a new period. `closed_at` is the evaluation time, while `last_detection_at` remains the lightning event time. The 10-second timer evaluates quiet periods. This is observed source silence, not proof that no lightning occurred.

At startup the watch first reports the source as unhealthy. A new connection becomes ready only after a valid decoded event on that connection, using the existing capture-specific readiness signal. A disconnect begins an open gap; the next valid event ends it. While disconnected, the period cannot close. A **fully bounded gap of at most 10 seconds (inclusive)** marks `coverage_uncertain=true` and increments `interruption_count`, but retains the original inactivity clock. Thus routine approximately 361-second socket rotations with 1–4-second gaps do not make closure impossible. This tolerance does **not** claim uninterrupted coverage or guarantee that no event was missed.

A gap longer than 10 seconds, an unbounded validity/watchdog gap, data loss, a missing gap boundary, or a worker-run change resets `healthy_since` to the recovery time. Closure then requires both the last event to be at least 30 minutes old and 30 minutes of healthy observation since recovery: `now >= greatest(last_detection_at, healthy_since) + 30 minutes`. After a long worker outage an active period remains open until a fresh valid event establishes readiness and the recovery condition is satisfied. No exact historical gap start/end is invented.

## Persistence and isolation

The additive migration under `scripts/activity-watch/migrations/` creates `ankara_activity_periods`, `ankara_activity_period_events` and a service-role-only `sync_ankara_activity_watch` RPC. Both tables enable RLS and grant no public/client access. The function is `SECURITY INVOKER`. It validates event keys and receive/event timestamps again and discards buffered deliveries over 30 seconds old rather than opening historical periods. Duplicate event keys are idempotent across retries and restarts. The worker omits the optional `p_now` argument so production evaluations use the database clock; local SQL tests inject a controlled clock. A period's `coverage_uncertain` is conservative and never cleared.

The worker sends bounded batches (50 events, 2,000 pending maximum) over the existing Supabase service-role connection, with one in-flight RPC, five-second abort timeout and capped retry delay. Overflow sets a loss marker; RPC failure retains the batch until a later attempt. A failure cannot throw into Ankara admission or publication. A process crash before a queued event is persisted may lose that event; a subsequent run marks an existing active period uncertain. If no period was durably opened before the crash, there is no way to reconstruct it without backfill, which is intentionally out of scope. The watch aborts an in-flight RPC as soon as a disconnect is observed, then retries with gap evidence. A database transaction that committed closure just before the abort cannot be retracted; this remaining race is unavoidable without coupling source transitions to the database transaction. Operators should review Continuous Capture health checkpoints around such a boundary.

## Rollout

Review and apply the migration deliberately to the intended Supabase database before enabling `ACTIVITY_WATCH_ENABLED=true` and deploying a worker containing this code. Leave the flag unset/false for a code-only rollout. This PR applies no migration and changes no environment variable, Fly machine or live database. Disabling the flag stops new Activity Watch traffic without changing archived periods. Historical period and event rows remain for a later export PR.
