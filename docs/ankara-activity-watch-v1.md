# Ankara Activity Watch v1

Activity Watch is an opt-in observer of the already decoded Blitzortung stream on the existing Ankara worker. `ACTIVITY_WATCH_ENABLED` defaults to disabled; this PR does not enable it. The existing Continuous Capture archive, candidate/incident lifecycle and publications have no dependency on its database responses. There is no second socket, backfill, notification, export or publisher.

## State and time

`idle` means no active row, `active` is the one open row, and `closed` is a finalized historical row. Only a technically valid event inside the existing Ankara monitoring polygon whose receive-minus-event latency is between 0 and the production Blitz admission freshness limit (30 seconds, inclusive) is offered to the watch. It does not reuse the production admission's in-memory dedupe or call its lifecycle callback. The same source fingerprint, SHA-256 hashed, is unique in the watch's event table and matches `continuous_capture_strikes.event_key`. These are observed detections, not inferred unique physical discharges. Independent asynchronous archive writes mean no foreign key to the archive; a watch event may be present when its archive write was lost or not yet committed.

The first eligible event opens a period at its event time. Distinct eligible events increment its count once and advance `last_detection_at` to the greatest actual event time. The database serializes sync operations under one advisory transaction lock and enforces one active period with a partial unique index. It closes at the first successful evaluation **at or after** `greatest(last_detection_at, healthy_since) + 30 minutes`; `closed_at` is the evaluation time, while `last_detection_at` remains the lightning event time. The 10-second timer evaluates quiet periods; an arriving event can also trigger evaluation. This is a period of observable source silence, not proof that no lightning occurred.

At startup the watch first reports the source as unhealthy. A new connection becomes ready only after a valid decoded event on that connection, using the existing capture-specific readiness signal. Disconnect, watchdog staleness or worker-run change makes the active period's coverage uncertain, increments its interruption count and clears `healthy_since`. On recovery, the whole 30-minute healthy-silence interval starts again. A short disconnect is never interpreted as a gap-free period. After a long worker outage an active period remains open until a fresh decoded event establishes readiness and 30 subsequent minutes of healthy silence have elapsed. The watch does not retroactively infer an exact gap start/end or claim complete coverage across interruptions.

## Persistence and isolation

The additive migration under `scripts/activity-watch/migrations/` creates `ankara_activity_periods`, `ankara_activity_period_events` and a service-role-only `sync_ankara_activity_watch` RPC. Both tables enable RLS and grant no public/client access. The function is `SECURITY INVOKER`. It validates event keys and receive/event timestamps again and discards buffered deliveries over 30 seconds old rather than opening historical periods. Duplicate event keys are idempotent across retries and restarts. The worker omits the optional `p_now` argument so production evaluations use the database clock; local SQL tests inject a controlled clock. A period's `coverage_uncertain` is conservative and never cleared.

The worker sends bounded batches (50 events, 2,000 pending maximum) over the existing Supabase service-role connection, with one in-flight RPC, five-second abort timeout and capped retry delay. Overflow sets a loss marker; RPC failure retains the batch until a later attempt. A failure cannot throw into Ankara admission or publication. A process crash before a queued event is persisted may lose that event; a subsequent run marks an existing active period uncertain. If no period was durably opened before the crash, there is no way to reconstruct it without backfill, which is intentionally out of scope. An outage concurrent with a closure RPC may still race with that database transaction; the next health sync records the interruption when a period remains open, but it cannot retract an already committed closure. Operators should review source-health records from Continuous Capture when assessing a boundary near an outage.

## Rollout

Review and apply the migration deliberately to the intended Supabase database before enabling `ACTIVITY_WATCH_ENABLED=true` and deploying a worker containing this code. Leave the flag unset/false for a code-only rollout. This PR applies no migration and changes no environment variable, Fly machine or live database. Disabling the flag stops new Activity Watch traffic without changing archived periods. Historical period and event rows remain for a later export PR.
