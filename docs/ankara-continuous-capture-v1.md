# Ankara continuous capture v1

This is a best-effort archive, disabled unless `CONTINUOUS_CAPTURE_ENABLED=true` (exact lowercase). Apply the separately reviewed migration in `scripts/continuous-capture/migrations/` before deployment and enablement. It uses the worker's existing `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`; no new credential, connection to Blitzortung, or publication path is introduced. No migration is applied by the worker.

## Admission and identity

The worker offers the already decoded, technically valid event to capture before `BlitzPrimaryAdmission`. It uses the decoder's `insideMonitoringArea`, computed using the same Ankara operational polygon and edge-inclusive membership function as the lifecycle. It does not require freshness, candidate creation, promotion, CG verification, or publication eligibility. Invalid/non-text/undecodable frames never reach capture. Future and old but technically valid source timestamps are preserved, not interpreted as evidence of current activity. The provider does not supply a trustworthy CG/IC classification here, so none is invented.

The existing `blitzFingerprint` source identity (raw time, coordinates and source metadata, excluding server and receipt time) is SHA-256 hashed and is the primary key. On-conflict ignore makes retries and cross-server/restart duplicates idempotent. If source identity fields differ, records are distinct even if they might describe the same physical flash. Raw timestamp and unit are stored alongside normalized milliseconds, reception time, location, server, and station count. The polygon identifier is a SHA-256 hash of the serialized actual polygon; compare against the polygon in source history to recover its boundary.

## Bounded operation

A single unreferenced two-second timer starts at most one request at a time. At most 2,000 strikes, 128 health rows, and 2,000,000 serialized row bytes are queued (including the in-flight batch); object overhead is additional but bounded by row counts. Each request contains at most 50 rows. The limits keep memory modest on a 256 MB machine and bound database traffic to at most one batch per tick; burst rates beyond sustained throughput will cause explicit loss. The queue stores only copied primitive fields; no candidate or incident object is shared. Supabase requests have a five-second abort timeout, up to three attempts, and 2/4/8-second retry delays. After the third failure the batch is dropped and degradation counted; no retry or database result reaches production admission. A single stuck request cannot spawn more requests or expand the queue beyond its limits. Shutdown requests one best-effort flush without waiting, so remaining rows can be lost.

## Coverage interpretation

The health table stores a process UUID, ordered sequence, source transitions and roughly one-minute checkpoints, with cumulative accepted, acknowledged, dropped and failure counts. `written` is the number of strike rows acknowledged by the API, including duplicates ignored by the database, not a unique-row count. Events have no dependency on the health table and vice versa. The source begins unknown, becomes healthy on a valid decoded event, and is marked unhealthy on connection transitions, disconnect, or the worker's existing valid-event timeout. A quiet Ankara polygon is compatible with healthy source coverage because health derives from the global stream, not local strikes. The watchdog detects stale validity at its existing 15-second cadence; the exact start of a gap is uncertain between the last valid event and detection. Reconnects preserve the queue and run ID, but create source transitions.

A checkpoint is evidence only of the reported state at that time, not proof of complete coverage between checkpoints. Treat process boundaries, missing or delayed checkpoints, dropped rows, nonzero failure counts, a queue backlog, abrupt shutdown, clock anomalies, and missing final records as uncertain. A total database outage or crash may prevent all health information from being saved, so absence of a record must never be interpreted as healthy coverage. Logs offer additional operational evidence but are not durable coverage guarantees. Queue drops and failures are cumulative for a process; health records themselves may be lost during an outage. No completeness claim is made across restarts.

Tables are isolated from manual Replay Capture Sessions and publication tables. RLS and grants restrict access to the service role. Chronological indexes support range queries and manual SQL deletion or storage inspection by an operator in a later phase; there is no automatic deletion, activity management, or export in this phase.
