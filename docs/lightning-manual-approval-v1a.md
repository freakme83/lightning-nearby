# Manual Approval Lifecycle v1A

The research end-to-end dry run still makes a technical shadow publish decision: `WOULD_PUBLISH` or `HOLD`. A separate human approval state answers a different question. `pending` awaits an operator; `approved` accepts that exact candidate; `skipped` declines it. Nothing is sent to X or any other publishing destination.

A newly inserted `WOULD_PUBLISH` row stores the **exact final composer text** in `message_text` and `approval_status = pending` in the same insert. A new `HOLD` row stores its exact text for audit with a null approval status. The fingerprint is checked against the exact text before insertion; approval only changes `approval_status`, `approval_updated_at`, and optional `approval_actor` from `GITHUB_ACTOR`. It cannot edit the message, fingerprint, provider identity, publication ID, or eligibility decision. These mutable approval fields are separate from the immutable `PublicationRecord` domain identity.

The migration adds nullable `message_text`, `approval_status`, `approval_updated_at`, and `approval_actor` columns to the existing private `public.publication_records` table, with a nullable check for `pending`, `approved`, or `skipped`. The two historical `WOULD_PUBLISH` records remain null: they are **not** silently made pending and are not actionable without a later explicit migration. RLS remains enabled; only server-side GitHub Actions uses the existing service-role credentials. No public policy or approval API is added.

Run **Research Lightning Manual Approval** with the `publicationId` from the end-to-end Job Summary and choose `approve` or `skip`. The workflow loads exactly that row and requires `WOULD_PUBLISH`, no platform post ID, valid stored message and fingerprint, and an actionable approval state. It atomically changes `pending → approved` or `pending → skipped` with a conditional PostgREST update constrained by publication ID, pending status, eligible decision, and null platform post ID. The update changes only approval metadata. If two operators race, one wins; the other reads the winner and reports `already_approved`/`already_skipped` for the same action or `transition_conflict` for the opposite action. Same-state retries succeed; there is no reset or reopen action.

A manually skipped row retains `decision = WOULD_PUBLISH`. It therefore remains in the existing v1B.1 duplicate-blocking history, just like an approved row. Approval does not change the provider event match, strict ±2-second/250-metre fallback, or lack of nearby cooldown. No publisher exists yet; a later X Publisher milestone may consider only `approved` records, subject to its own safety checks.

The manual workflow uploads a short-lived structured result and shows the exact stored message in its Job Summary. Rejected transitions and storage failures fail the workflow with a clear outcome; rerunning an already-completed same action succeeds. The existing end-to-end summary shows `pending` and the publication ID only when an eligible record was actually inserted. Both workflows continue to say that nothing was published.

GitHub requires a new `workflow_dispatch` file to exist on the repository's default branch before its manual Run workflow control becomes available. The repository's default branch is currently `main`, while this draft PR targets `merge-ready`. The new workflow may therefore need a later promotion to `main` before the GitHub UI acceptance steps can be run. This PR does not change or merge either integration branch.
