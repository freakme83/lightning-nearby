# Research: WebSocket incident gate versus Xweather checks

This bounded experiment asks whether the observational LightningMaps-compatible WebSocket → local filtering → clustering → incident lifecycle could avoid Xweather requests during quiet periods while issuing requests for meaningful incidents. It measures **trigger and cost behavior**, not safety-grade recall or provider equivalence. It does not change the production `/api/lightning/live` path: that path requests Xweather Summary and only requests Flash when Summary is healthy and positive.

## Run and boundaries

```sh
npm run research:lightning-gate-compare -- --duration=15 --area=ankara --max-xweather-calls=3 --hypothetical-user-checks=12
npm run research:lightning-gate-compare -- --duration=10 --box=41.08,1.22,40.84,0.98 --max-xweather-calls=0
```

`--box=north,east,south,west` uses the existing custom research box; `--area=ankara` subscribes to the enclosing box and applies the existing strict polygon locally. The listener cannot guarantee server-side geographic filtering. Existing profile B is the default; A/C can be selected with `--incident-profile`. Duration is 1–20 whole minutes; the default is 15. There is no region search, schedule, polling, persistence, or application integration. The experiment uses the existing source-health, local fresh observation, cluster, and publish-policy behavior unchanged. JSONL stdout contains `run_start`, source health/connection events, incident eligibility and explicit Xweather skip reasons, request start/result, periodic summaries, and `gate_final_comparison_summary`. Keep the run bounded even if the request budget is exhausted.

The comparison uses a **separate controller** from the one-shot paired-validation harness. Only a `WOULD_PUBLISH` incident with wall-clock age `Date.now() - lastActivityTimeMs` in **0–240,000 ms** is directly eligible. A stale startup publish is skipped without spending a call; if that same already-published active incident later receives accepted fresh activity, its current coordinate and current `lastActivityTimeMs` may qualify without a second publication decision. Future/invalid times are ineligible. Candidates, expired candidates, arbitrary active updates, cooldown suppressions, and duplicate activity in an already enriched incident do not request Xweather. The distinct incident-ID request set is bounded by the configured cap. The default cap is **3**, valid range **0–10**, with `0` a provider-free dry run. Missing credentials (`XWEATHER_CLIENT_ID`, `XWEATHER_CLIENT_SECRET`) cause explicit zero-request skips. A failed request remains `provider_unavailable`, never `no_match`. The request uses the existing `/lightning/closest` adapter and its 10 km query, 8 km local match, and ±5 minute defaults without alteration.

The final JSONL summary includes feed messages/decoding/dedupe and subscription-box versus strict-area acceptance; local fresh/stale/future observations and source interruptions; clusters, candidates, promotions, publish decisions and suppressions; gate eligibility/skip counts and reactivations; actual request count, enrichment states, and cost-header diagnostics. `knownHeaderTokenSum` adds only reported `X-Cost-Tokens`. If any attempted request lacks a valid header, `totalTokensWhenFullyKnown` is `null`, never a fabricated zero. The gate issues zero requests while no qualifying incident exists. Request errors are sanitized; authenticated URLs and credentials are not logged.

With optional `--hypothetical-user-checks=N`, the summary also reports **N–2N observed-planning tokens**: N if all hypothetical production Summary checks were healthy zero, 2N if all were Summary positive and Flash ran. These are parameters based on previous production request observations (roughly 1 token for Summary and 1 more for Flash), **not measured counterfactual outcomes or billing guarantees**. The experiment has no evidence for how many hypothetical checks would have been positive. Summary → Flash and `/lightning/closest` have different request shapes and meanings, and pricing can change. No percentage savings or recall-equivalence claim follows from this comparison.

WebSocket feed completeness, lossless delivery, real-time delivery, strict server-side geography, exact flash identity between providers, safe replacement of Xweather Summary, and public production suitability remain unproven. Absence of a feed incident is not evidence that no lightning occurred. This is not a publisher, notification system, or production live UI.

## Future UI observation (not implemented)

The promoted incident already has a representative coordinate suitable for a separate approximate-place lookup. Existing research labels include `Aşağı Ayrancı, Çankaya`, `Beynam, Balâ`, `Yenipeçenek, Sincan`, and `Alacaatlı, Çankaya`. A future prototype could show **incident place context** such as `Aşağı Ayrancı / Çankaya civarı` alongside **user-relative nearest observation** such as `8,0 km güneybatı · 2 dk önce`. These answer different questions: the normalized `displayLabel` approximates an incident area; distance/direction is relative to the monitored user's location. OSM hierarchy varies, so the generic label is not an authoritative neighborhood or an exact strike address. This experiment makes no Nominatim call and implements no UI.
